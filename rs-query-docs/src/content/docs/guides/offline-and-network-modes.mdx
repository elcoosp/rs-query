rs-query reproduces TanStack v5's offline story: a per-query `NetworkMode` decides whether fetches *start* and whether retries *continue*, an `OnlineManager` tracks connectivity, and paused work resumes automatically on reconnect. This guide wires the whole loop.

## Pick a network mode

`NetworkMode` has three variants with TanStack-exact semantics:

| Mode           | Fetch starts offline? | Retries continue offline? | Typical use                     |
| -------------- | --------------------- | ------------------------- | ------------------------------- |
| `Online`       | No — the fetch is paused | No — in-flight retries pause | The default for queries      |
| `Always`       | Yes                   | Yes                       | Local-first work, IPC, storage  |
| `OfflineFirst` | Yes — the first attempt runs | No — retries pause   | Write-then-retry mutations      |

<Code lang="rust" code={`use rs_query::{NetworkMode, QueryOptions};

let options = QueryOptions::default().network_mode(NetworkMode::OfflineFirst);`} />

The helpers `can_fetch(mode, online)` and `can_retry(mode, online)` encode the matrix if you need the decision in your own code.

## Drive connectivity

`OnlineManager` starts online and takes truth from your platform's connectivity callbacks — there is no OS listener baked in, which keeps the crate runtime-free:

<Code lang="rust" code={`use rs_query::OnlineManager;

let online = OnlineManager::new(); // starts online

// Wire these to your platform:
online.set_online(false); // in-flight retries pause; new fetches pause per mode
online.set_online(true);  // paused work resumes`} />

The client owns one: `client.online_manager()` returns it, and `client.handle_reconnect()` runs the full reconnect sequence — refetch triggers for queries and `resume_paused_mutations`.

## Pause and resume behavior

While offline:

- Queries in `Online` mode do not start; their fetch status reports `Paused`.
- An `OfflineFirst` mutation runs its first attempt, then pauses before retries.
- `Always` work continues untouched.

When connectivity returns, paused fetches resume from where they stopped — attempt counts and backoff state survive the pause.

## Refetch on reconnect

Control whether stale data refreshes when the connection comes back, and how eagerly:

<Code lang="rust" code={`use rs_query::{QueryOptions, RefetchTrigger};

let options = QueryOptions::default()
    .refetch_on_reconnect(RefetchTrigger::Always) // even fresh data refetches
    .refetch_on_mount(RefetchTrigger::Enabled)    // default: refetch if stale
    .refetch_on_window_focus(RefetchTrigger::Disabled);`} />

`RefetchTrigger` has three variants: `Enabled` (refetch when stale — the default), `Always`, and `Disabled`.

<Aside type="note">
Focus and reconnect refetches run through the same `refetch_queries` pipeline as manual calls, so filters, deduplication, and cancellation all apply.
</Aside>

## Mount and unmount lifecycle

`client.mount()` and `client.unmount()` book the client's global handlers — focus/online subscriptions and the GC sweep. Call `mount` when your app starts and `unmount` on shutdown; the pause-on-unmount cancel path uses `QueryError::Cancelled { revert: false, silent: true }` so nothing surfaces as a spurious error.

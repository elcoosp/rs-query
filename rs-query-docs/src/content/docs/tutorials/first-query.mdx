In this tutorial you build the smallest useful rs-query program: a `QueryClient`, one `Query` with a `QueryKey`, and a single awaited fetch. You then invalidate the key and watch the cache respond. This is the golden path that every rs-query application — headless or framework-bound — builds on.

<Aside type="note">
You need a working Rust toolchain (stable, edition 2024) and the [quoin](https://github.com/elcoosp/quoin) repository checked out as a sibling directory, because rs-query depends on it by path. See [Installation](/rs-query/guides/install/) if you have not set this up yet.
</Aside>

## 1. Create the project

Create a binary crate next to your `rs-query` and `quoin` checkouts:

```bash
cargo new query-demo
cd query-demo
```

Point `Cargo.toml` at the local checkouts. The path layout matters: `quoin` resolves as `../quoin/quoin-core` from a sibling directory.

```toml
[dependencies]
rs-query = { path = "../rs-query" }
tokio = { version = "1", features = ["rt-multi-thread", "macros"] }
```

`rs-query` itself does not need tokio — it runs on quoin's shared worker pool by default. The demo uses tokio only for its own `main`.

## 2. Create a `QueryClient`

The client owns the cache, the deduplication table, and the runtime. It is cheap to clone, and every clone shares the same cache.

```rust
use rs_query::QueryClient;

fn main() {
    let client = QueryClient::new();
    println!("client ready");
}
```

Hold the client in your application state for the lifetime of the program.

## 3. Define a query

A `Query` pairs a `QueryKey` with an async fetch closure that returns `Result<T, E>`. Keys are hierarchical: `QueryKey::new("users")` creates the `"users"` segment, and `.with("id", 42)` appends a labelled segment.

```rust
use std::time::Duration;
use rs_query::{Query, QueryClient, QueryKey};

let client = QueryClient::new();
let key = QueryKey::new("users").with("id", 42);

let query = Query::new(key.clone(), || async {
    Ok(vec!["Ada", "Alan"])
})
.stale_time(Duration::from_secs(30));
```

The `stale_time(30 s)` line tells the cache that the data stays fresh for thirty seconds after a successful fetch.

## 4. Run it with `spawn_query`

`spawn_query` submits the fetch to the client's runtime and returns a `SpawnedTask` — an awaitable handle you can also abort by dropping it.

```rust
use rs_query::spawn_query;

let handle = spawn_query(&client, &query);
let state = handle.await;

assert!(state.is_success());
println!("data: {:?}", state.data());
```

Run the demo:

```bash
cargo run
```

You should see the fetched names printed from cache.

<Aside type="tip">
Dropping a `SpawnedTask` aborts the fetch cooperatively through a `CancellationToken`. This is the mechanism behind cancel-on-unmount in framework apps.
</Aside>

## 5. Read the state machine

`state` is a `QueryState<Vec<&str>>` — an enum with one variant per cache situation:

```text
Idle → Loading → Success(T)
              → Error { error, stale_data }
Success(T) → Stale(T) → Refetching(T) → Success(T)
```

After the awaited call in step 4 you hold `Success`. Call `state.is_stale()` after `stale_time` has elapsed to see the transition to `Stale`.

## 6. Invalidate the key

Mark the `"users"` prefix stale, refetching only the queries that currently have an active observer — the TanStack default:

```rust
use rs_query::{InvalidateQueryFilters, QueryFilters, RefetchType};

client.invalidate_queries_filtered(
    InvalidateQueryFilters::new()
        .filters(QueryFilters::with_key(QueryKey::new("users")))
        .refetch_type(RefetchType::Active),
);
```

Every query whose key starts with the `"users"` segment is now stale, and active ones refetch immediately.

## What you built

A client, a keyed query, a spawned fetch, and filtered invalidation — the four moves that repeat in every rs-query application. From here, wire the same client into a UI framework, or keep going headless with imperative fetching.

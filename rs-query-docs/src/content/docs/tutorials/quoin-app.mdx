In this tutorial you take the headless query from the [first tutorial](/tutorials/first-query/) and observe it from inside a quoin application. The bindings are generic over any `quoin_core::ReactiveContext`, so the code below is identical on gpui, leptos, dioxus, xilem, and floem — only the surrounding view syntax differs. Every binding returns your framework's **own** signal type.

<Aside type="note">
Prerequisites: a quoin application skeleton with a `ReactiveContext` available (usually `cx`), and the [installation](/guides/install/) from the first tutorial.
</Aside>

## 1. Build the client from the framework context

Construct the client with `QueryClient::with_context(&cx)` so fetches and timers ride the framework's own executor instead of the default worker pool:

<Code lang="rust" code={`use rs_query::QueryClient;

// Inside your app setup:
let client = QueryClient::with_context(&cx);`} />

Store the client in your application state. Like `QueryClient::new()`, it is cheap to clone and shares one cache across clones.

## 2. Observe a query from a view

Inside a component, call `use_query` with the context, the client, and the query. The binding pumps cache updates into a framework signal and stays in sync through lag-tolerant cache pumps:

<Code lang="rust" code={`use rs_query::use_query;

// Inside a component, where cx is the framework's ReactiveContext:
let todo = use_query(&cx, &client, &query);

// todo.state is the framework's own signal: read it from your view.
let state = todo.state.get(); // QueryState<Todo>`} />

Dropping the binding cancels its pump and aborts the in-flight fetch — cancel-on-unmount is the default behavior, not an opt-in.

## 3. Render the state

`QueryState<T>` has a variant for every cache situation, so `match` covers rendering exhaustively:

<Code lang="rust" code={`match state {
    rs_query::QueryState::Idle | rs_query::QueryState::Loading => render_spinner(),
    rs_query::QueryState::LoadingWithPlaceholder(data)
    | rs_query::QueryState::Success(data)
    | rs_query::QueryState::Stale(data)
    | rs_query::QueryState::Refetching(data) => render_todo(data),
    rs_query::QueryState::Error { error, stale_data } => match stale_data {
                    Some(data) => render_todo_with_banner(data, error),
                    None => render_error(error),
    },
}`} />

<Aside type="tip">
You rarely write this match by hand. The [QueryObserver](/reference/observers/) result flags — `is_placeholder_data`, `is_refetch_error`, `is_paused` — exist to turn these branches into compact boolean logic.
</Aside>

## 4. Trigger a refetch from the view

The binding exposes `refetch` and `abort_fetch` for user-driven actions:

<Code lang="rust" code={`todo.refetch();     // re-run the query now
todo.abort_fetch(); // cancel the in-flight fetch`} />

## 5. Mutate and invalidate

Wire a save button to a mutation with `use_mutation`, and invalidate the list key on success. The mutation lifecycle runs cache-level and options-level hooks in TanStack order (see [Mutations and optimistic updates](/guides/mutations/)):

<Code lang="rust" code={`use rs_query::{Mutation, MutateOptions};

let save = use_mutation(&cx, &client, &save_mutation);

// On button click:
save.mutate(patch, MutateOptions::new().on_success(|_client, _data| {
    // the mutation's own invalidates_key already refetched active queries
}));`} />

The signal updates again when the invalidated query refetches — no manual wiring between mutation and view.

## 6. Gate rendering during hydration

If the client restores persisted state at startup, hold the `is_restoring` flag until the restore finishes. Bindings respect the gate and hold `fetchStatus` at `idle` while it is set:

<Code lang="rust" code={`client.set_is_restoring(true);
// ... restore ...
client.set_is_restoring(false);`} />

## What you built

A framework-bound query with cancel-on-unmount, exhaustive state rendering, user-driven refetch, mutation-driven invalidation, and a hydration gate — the full reactive loop, without a single framework-specific import in the query layer.
